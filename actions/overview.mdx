Actions let a conversation request useful work. A prompt describes when to act; saved permissions, connections and current state decide whether the action can run.

| Action | Guide | Result to check |
| --- | --- | --- |
| Calendar booking | [Cal.com](/actions/calcom) · [Google Calendar](/actions/google-calendar) | Calendar mutation succeeded |
| Booking read-back | [Confirmation](/actions/booking-confirmation) | Current details approved before mutation |
| Text during a call | [In-call SMS](/actions/in-call-sms) | Accepted send, then delivery if available |
| Human handoff | [Transfer](/actions/transfer) | Actual handoff state |
| End a conversation | [End call](/actions/end-call) | Confirmed terminal call state |
| Give a caller time | [Wait](/actions/wait) | Bounded expected silence |
| Navigate a switchboard | [Phone menus](/actions/ivr-navigation) | Menu exit or timeout |
| Call your service | [Custom functions](/advanced/custom-functions) | Your authenticated action result |

## Tags request work

Tags such as `[SEND_SMS: message]`, `[END_CALL]` and `[WAIT]` are interpreted by the relevant call path rather than spoken as ordinary text. They are not proof that the requested work completed. Multiple actions in one response are not an atomic transaction; one can succeed while another fails.

Keep instructions narrow. Describe the trigger, required information and what to say when an action cannot be confirmed. A booking success should not be described as a delivered confirmation text, and an accepted transfer should not be described as an answered human call.

## Channels have different capabilities

Telephone actions do not automatically become website actions. Public website visitors cannot use the built-in telephone booking, SMS, transfer, keypad or menu functions. Enabled custom functions need separate review for public visitor access.
