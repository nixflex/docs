Caller context helps an agent recognise a returning telephone caller and continue a useful conversation. It can include a name, summary and saved information. It is context to check with the person, not proof of identity.

## Memory and greetings are separate

`remember_callers:false` stops ordinary telephone context use and learning. It does not delete existing records or prevent deliberate caller-context API writes. `greet_by_name:false` disables the dedicated inbound name-greeting hint; it is not a global anonymisation control.

| Remember callers | Greet by name | Result |
| --- | --- | --- |
| On | On | Context and the saved-name greeting may be used |
| Off | On | Ordinary memory is off; a saved name can still be used in the greeting |
| On | Off | Memory remains available without the dedicated greeting hint |
| Off | Off | Both ordinary memory and the dedicated hint are off |

## Where information comes from

Saved caller records can be learned from permitted telephone work or managed through the caller-context API. A recent call record, caller memory and a campaign recipient's variables are different data. Do not assume every field is a durable memory or that clearing a transcript clears the caller record.

Website visitor cards and messages are separate from telephone memory. A visitor's name, email and phone number are self-reported. Browser recognition can end when storage changes and does not verify identity.

## Retention and correction

Call retention controls call data. It is not a blanket promise to delete every caller, message, integration record or customer-owned recording after the same period. Use the documented caller-context update or deletion route for that record, and check the response before declaring it removed.
