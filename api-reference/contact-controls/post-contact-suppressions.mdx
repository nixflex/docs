Add account-owned do-not-contact entries for future contact checks. Existing entries are retained; a new owner request cannot replace recipient opt-out evidence.

## Authentication

Send `Authorization: Bearer KEY_ID:KEY_SECRET` using the owning account’s server-side credential. Send `Content-Type: application/json`.

## Request fields

Send a JSON object.

| Field | Type | Required | Default | Limits and meaning |
| --- | --- | --- | --- | --- |
| `phone_numbers` | array of string | Yes | None | One to 1,000 strict E.164 numbers. Maximum 1000 items. Minimum 1 items. |
| `channel` | string | No | `"all"` | Channel bucket. Allowed: `"all"`, `"voice"`, `"sms"`. |

Repeated values do not create duplicate entries in the same account/channel bucket. This changes future contact permission, not already accepted contact. Existing opt-outs remain enforced even if adding owner suppressions is temporarily paused.

## Response fields

`200 OK` returns the shape below. Nullable fields can be unknown or unset; do not turn null into zero or false.

| Field | Type | Meaning |
| --- | --- | --- |
| `added` | integer | New stored entries; existing matches and duplicate input rows add nothing. |
| `submitted` | integer | Number of submitted input rows, including duplicates. |
| `channel` | string | Chosen stored bucket. Allowed: `"all"`, `"voice"`, `"sms"`. |

## Example request

The examples use staging. Keep `NXF_STAGING_KEY` in your environment; the CLI uses it through `NIXFLEX_API_KEY`. The shell examples use Bash syntax. Tabs labelled **direct HTTP** do not rely on an SDK or CLI method; the reviewed kit has no matching method.

<RequestExample>

```bash cURL
curl --request POST \
  --url "https://nixflex-voice-engine-staging.up.railway.app/v1/contact-suppressions" \
  --header "Authorization: Bearer $NXF_STAGING_KEY" \
  --header "Content-Type: application/json" \
  --data '{"phone_numbers":["+12025550101"],"channel":"all"}'
```

## Errors

Failures return an `error` object with `code`, `message`, `doc_url` and optional details. Each code links to the shared error catalog. Read the message and details before deciding whether to resend.

<div className="agent-error-table">

| Status | Code | Meaning | What to do |
| --- | --- | --- | --- |
| 400 | [`invalid_request`](/api-reference/errors#invalid_request) | The identifier or request fields are invalid. | Correct the documented fields before resending. |
| 503 | [`feature_paused`](/api-reference/errors#feature_paused) | This control is paused. | Wait for availability; do not work around the refusal. |
| 503 | [`outcome_unknown`](/api-reference/errors#outcome_unknown) | The write result could not be confirmed. | Read current state; do not resend automatically. |
| 400 | [`invalid_json`](/api-reference/errors#invalid_json) | Invalid JSON body. | Correct JSON syntax. |
| 413 | [`payload_too_large`](/api-reference/errors#payload_too_large) | The request exceeds the JSON body limit. | Send a smaller request. |
| 401 | [`unauthorized`](/api-reference/errors#unauthorized) | The credential is missing or invalid. | Check the account credential and environment. |
| 429 | [`rate_limit_exceeded`](/api-reference/errors#rate_limit_exceeded) | The account request limit was reached. | Wait for Retry-After. Reconcile uncertain writes before resending. |

</div>

## Retry and idempotency

No idempotency key is documented. A timeout or 5xx can follow a committed change. Read the current state before deciding whether to submit again; never automatically repeat an uncertain write. Repeating the same values does not add duplicate rows, but an uncertain result should still be checked with the list endpoint.
