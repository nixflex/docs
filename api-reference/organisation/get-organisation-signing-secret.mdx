Explicitly retrieve the organisation signing secret for verifying event deliveries. Keep the result in a private secret store; never expose it in logs, chat or tool output.

## Authentication

Send `Authorization: Bearer KEY_ID:KEY_SECRET` for server-side organisation API-key authority, or a verified personal dashboard Bearer session. The shared API key has Owner authority for these methods; keep it server-side. A personal session is checked against current membership and MFA. Personal access is Owner only. The environment must have organisations enabled; otherwise these routes return 404. Personal invitation acceptance, leaving and ownership transfer are separate dashboard flows and are not API-key methods.

## Request fields

No request body or query fields are required.

The organisation context and member list never contain this secret. Signing-secret retrieval is a private Owner action in the dashboard and is excluded from every kit. No executable request is provided. Retrieve it privately through the Owner workflow.

## Response fields

`200 OK` returns the shape below. Nullable fields can be unknown or unset; do not turn null into zero or false.

| Field | Type | Meaning |
| --- | --- | --- |
| `signing_secret` | string | Private organisation signing secret. Independent of API-key rotation. |

## Example request

Dashboard only. An Owner must view the signing secret privately in the dashboard. This action is excluded from Node, CLI, Python and MCP. No executable example is provided.

Failures return an `error` object with `code`, `message`, `doc_url` and optional details. Each code links to the shared error catalog. Read the message and details before deciding whether to resend.

## Retry and idempotency

This is a read-only request. Retry transient connection or server failures with bounded backoff; respect Retry-After for 429. Do not retry validation or ownership errors unchanged. A later read can return newer state.
