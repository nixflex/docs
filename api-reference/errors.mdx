Use the HTTP status and machine-readable code together. Messages can become more specific without changing the code. Never automatically retry a write; follow [Retries and idempotency](/api-reference/retries).

## Response shape

```json
{
  "error": {
    "type": "authentication_error",
    "code": "unauthorized",
    "message": "Invalid or missing API key",
    "doc_url": "https://docs.nixflex.com/errors/unauthorized",
    "details": {}
  }
}
```

The standard API error helper returns this object. Details are operation-specific and can be empty; they can include field names, resource IDs, or a request ID. Do not assume every upstream, disabled-feature, or legacy response has the complete envelope. Check the status first and keep a fallback for non-JSON or incomplete errors.

## Status and type

| HTTP status | Standard error.type | Meaning |
| --- | --- | --- |
| 400, 422 | invalid_request | Invalid input or content. |
| 401 | authentication_error | Missing or invalid authentication. |
| 402 | payment_required | Payment refusal when an operation uses this status. |
| 403 | permission_denied | Operation is not permitted. |
| 404 | not_found | Owned resource unavailable. |
| 409 | conflict | Current state conflicts with the request. |
| 429 | rate_limit | Request or resource limit reached. |
| 500–599 | server_error | Service failure or uncertain outcome. |
| Other statuses, including 410, 413, 415 | error | Read the specific code and message. |

A credit refusal can be 409 rather than 402. Follow its actual code and status. A job can contain a failure code inside an otherwise successful job-read response; the catalog gives the status when that failure is returned as an HTTP refusal.

## Error links

The engine supplies links under `/errors/<code>`. Each known public code redirects to the matching section of this catalog. Historic carrier refusals use neutral descriptions below; their original links still resolve. Keep unknown codes in safe diagnostics and use the general error guidance when no specific entry exists.

## Catalog

Codes are alphabetical. Some codes have more than one status because their read, validation, and state-check contexts differ. Details and the endpoint determine the exact recovery action.

## Contact-policy names and outcomes

Single-call and single-SMS refusals use `outside_hours` or `needs_timezone` (409), or `contact_policy_unavailable` (503). Their details can explicitly report `outcome: not_sent`, `sent: false` and `charged: false`. The message ends with `Nothing was sent or charged for this attempt.` Local-window advice can change the preceding text.

`single_contact_policy` is the internal policy-check name; `refused_before_dispatch` is a dispatch outcome marker. Neither is a universal HTTP error code. Match `error.code` and inspect the documented receipt. An unknown outcome is not proof of a refusal or a safe resend.
