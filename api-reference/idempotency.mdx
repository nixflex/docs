Idempotency is supported only where an operation documents it. Sending `Idempotency-Key` to any endpoint does not make every write safe to repeat.


## Knowledge operations

Use the documented key for one intended operation. Preserve the same key, target and payload when reconciling that operation. A changed payload under a used identity can return **409 `idempotency_conflict`**. Revision guards such as `base_revision` prevent an update from silently replacing newer work; they are separate from request identity.

An accepted job can be returned on replay. Save its ID and poll the [job read](/api-reference/knowledge/get-knowledge-jobs-id) instead of submitting another job. `202 Accepted` does not mean the content was published. Check its final state and error.

Each endpoint lists its required key, limits and revision rules. Do not assume the same retention window or replay behavior applies to all operations.

## Calls, SMS and other writes

Agent creation, outbound calls without request_id, SMS, campaigns and key rotation have no general replay promise. A connection failure can happen after work starts. Read the resource or receipt and reconcile the result before any deliberate new attempt.

Contact-policy refusals can explicitly report `outcome: not_sent`, `sent: false` and `charged: false`. An unknown outcome does not provide that guarantee. Internal names such as `single_contact_policy` are not a client idempotency mechanism.

## Client behavior

Disable automatic write retries in your HTTP client, SDK, proxy and job queue. Keep safe correlation identifiers, but do not log credentials, message bodies or caller context. See [retry guidance](/api-reference/retries) for the recovery steps.

## Reconcile an outbound request UUID

Save one UUID before the first request for an intended call. Persist it with the request payload so a process restart cannot accidentally create a new intent. Supply it as the JSON field `request_id`, not an Idempotency-Key header.

| Result | What it proves | Next action |
| --- | --- | --- |
| 201 initiated | A call was accepted; completion is still unknown. | Save call_id and request_id; read the call. |
| 200 replayed:true | This UUID already has an accepted call. | Use the same call_id; no second dispatch occurred. |
| 409 outbound_request_pending / outbound_request_unknown | The existing intent cannot be launched again. | Keep the UUID and read request status. |
| 409 request_id_conflict | The same UUID was used with changed input. | Reconcile the original payload; do not automatically replace the UUID. |
| 503 with details.safe_to_retry:false | The journal or launch outcome is uncertain. | Keep the UUID and use bounded status reads. |

A 201 can also include `request_status:"unconfirmed"` and `safe_to_retry:false`: the call ID is known even though the final journal acknowledgement was lost. Never redial it. A new UUID is a new explicit call intent. Requests without request_id retain their existing behaviour and have no launch replay protection.

Read [outbound request status](/api-reference/calls/get-outbound-request). A 404 or an empty history page does not prove that an uncertain call was never placed.
