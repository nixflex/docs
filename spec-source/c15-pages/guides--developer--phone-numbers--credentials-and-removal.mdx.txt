## Choose the operation

Use [update credentials](/api-reference/phone-numbers/credentials) when the connection remains wanted but its carrier credentials change. Use [remove number](/api-reference/phone-numbers/delete) only when disconnecting is the actual intention. Moving agents is a separate [number PATCH](/guides/developer/phone-numbers/routing-and-overrides).

The credential endpoint accepts exactly the pair documented for the existing carrier. It refuses mixed pairs, extra settings, agent fields and carrier switches. Keep the credential payload in your private server secret process; do not copy it into logs or shell arguments.

## Replace credentials in place

Verification checks ownership of the exact number before routing is changed. The number ID, agent assignment, prompts, channel switches, integrations and history remain. A successful response identifies the number and carrier with `updated:true`; it does not return a secret or a full resource snapshot.

Changed credential identity can clear callback-verification evidence while retaining a saved public key. Follow the existing fresh test-call and approval flow where required. Identical current credentials retain verification only when the resource also matches.

After a lost response, read current state and reconcile the existing operation. Stop automatic retries on `carrier_outcome_unknown`. A `credential_save_pending` result permits only deliberate completion with identical input after review. Do not delete and re-import to recover from a credential update.

## Remove deliberately

Removal has external routing cleanup and local completion steps. It does not guarantee cancellation of carrier rental or deletion of a separate carrier account. Check the current operation state and authorised cleanup path before submitting once.

An initial unconfirmed cleanup can return 503 `number_cleanup_uncertain`; an exact retry while still uncertain returns 409 with the same code. A conflicting operation returns `number_operation_pending`. Confirmed carrier change with database completion unknown can return `number_save_pending`; a deliberate exact retry resumes completion without another carrier write. This is not permission for an automatic retry loop.

## Decide from the actual result

| Code or result | Next step |
| --- | --- |
| `carrier_mismatch` | Use credentials for the existing carrier; this route does not migrate it. |
| `invalid_credentials` | Correct the private pair and verify its account ownership. |
| `number_cleanup_credentials_missing` | Restore the supported cleanup credentials before removal. |
| `number_cleanup_uncertain` | Preserve the pending operation and seek reconciliation. |
| `number_save_pending` | Reconcile local completion with the same intended operation. |
| Confirmed removal | Verify the resulting connection state; handle external rental separately. |
