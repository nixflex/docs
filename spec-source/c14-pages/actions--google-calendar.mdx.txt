## Connect and return to your app

Owner and Admin personal sessions can change the connection; Members can read status. An organisation API key acts for the organisation and stays on the server. Do not expose it to work around a person's role.

Assign an agent to the number, then [create a consent link](/api-reference/integration-settings/google-calendar) with your HTTPS `return_url`. Open the returned URL in the user's browser. The link lasts ten minutes and can be used once. A custom app scheme needs operator approval first.

On return, read `status=connected` and `phone_number`, or `status=error` with `access_denied`, `expired_link`, `already_connected` or `google_error`. Reserved result parameters are replaced while ordinary query parameters remain. OAuth credentials never return to your app. Expired state without a trusted destination displays a local error.

Replace the example number with the owned number and use your app’s actual HTTPS return URL. Keep the account credential on the server. This request creates a consent link; the user must still authorise the connection.

<CodeGroup>

```bash cURL
curl --request POST \
  --url 'https://api.nixflex.com/v1/integrations/google-calendar/number/%2B12025550123/connect' \
  --header "Authorization: Bearer $NIXFLEX_API_KEY" \
  --header 'Content-Type: application/json' \
  --data '{"return_url":"https://app.example.com/calendar/return"}'
```

## Show the current state

[Read status](/api-reference/integration-settings/google-calendar-status) when the connection screen opens or regains focus. `connected: false` means not set up. `connected: true, needs_reconnect: true` means new consent is needed. A 503 means the check failed; it is not proof of disconnection. Reconnect preserves business settings.

## Configure availability and invitations

[PATCH settings](/api-reference/integration-settings/google-calendar-settings) for timezone, all seven days of working hours, slot length and calendar ID. Only one booking provider can be active for a number. A Cal.com conflict must be resolved deliberately before connecting Google Calendar.

`send_invites` defaults to true, including existing connections without a stored value. When on, Google is asked to email the caller an invitation, update or cancellation. Google controls delivery; the engine does not add the owner as an attendee or send a separate owner email. When off, no Google notification is requested. Omit the field to keep its saved value.

## Confirm the person, then book

Ask the name, read it back and wait for a clear yes. Then ask the email, spell its local part and wait for a separate yes for the full address. Say an exact familiar domain as words, for example `s-a-m at gmail dot com`; spell an unusual domain too. Saved addresses follow the same rule. A correction clears that field’s old approval; a yes to one clarified letter is not approval of the whole address. Looking up, moving or cancelling an existing appointment needs email approval without a new name question.

These contact approvals are separate from the optional final action/time approval controlled by `require_booking_confirmation`. See [booking confirmation](/actions/booking-confirmation). Say “Google will email you an invite” when requested; do not claim it reached an inbox. Claim a text was sent only after actual matching carrier acceptance.

## Reconcile the result

Read the calendar result and signed [booking webhook object](/api-reference/webhooks#booking-object). A saved setting or consent link is not booking proof. Duplicate lookup confirmations do not create another public booking event. If access must end, [disconnect this number](/api-reference/integration-settings/google-calendar-disconnect); already dispatched provider work cannot be recalled.

After a call, use [`call.bookings`](/api-reference/call-bookings) for the ordered confirmed actions and final result for each booking. Creating and then cancelling produces zero active bookings. SMS continues to use `sms.booking` per reply, with no delayed thread aggregate.

## Read the booking result

Use [GET call booking results](/api-reference/calls/get-bookings) after the call. `ready` includes the confirmed timeline and final booking rows. `none` confirms no successful mutations only when the retained evidence is complete. `processing`, `deleted` and `unavailable` each return `result:null` and must remain distinct in your UI.

## Errors and what to do

| Code or result | What it means | What to do |
| --- | --- | --- |
| `agent_not_assigned` | This number has no eligible agent. | Assign the intended owned agent, then start consent. |
| `booking_provider_conflict` | Another booking provider is active. | Choose one and disconnect the unwanted connection deliberately. |
| `expired_link` / `access_denied` | Consent did not complete. | Explain the result and offer a deliberate fresh consent flow. |
| `invalid_hours` / `invalid_timezone` | Availability settings are invalid. | Send all seven days and a valid IANA time zone. |
| `needs_reconnect:true` | Saved consent needs renewal. | Ask the authorised person to reconnect; preserve business settings. |
| 503 status read | Connection state could not be checked. | Keep state unknown and retry the read with a limit. |
| Lost settings response | The change may have been saved. | Read status/settings before another deliberate write. |
