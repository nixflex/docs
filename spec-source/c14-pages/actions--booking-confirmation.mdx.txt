## Prerequisites

Keep the account credential in `NIXFLEX_API_KEY` on your server. Use an owned agent and a number with the intended calendar connection. Match the host and key to the same environment. This update changes future agent behaviour.

## 1. Read the current settings

Read the agent and any relevant number override before changing shared behaviour. A prompt alone cannot grant an action capability.

## 2. Save the intended setting

Node and Python below use their standard HTTP clients. Keep `NIXFLEX_API_KEY` on the server. The CLI examples require a kit version supporting the command; see [release status](/sdks/ecosystem). No example retries a mutation automatically.

```bash cURL
curl --fail-with-body --request PUT \
  --url "https://api.nixflex.com/v1/agents/agent_example" \
  --header "Authorization: Bearer $NIXFLEX_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{"require_booking_confirmation":true}'
```

```python Python
import os, json
from urllib.request import HTTPRedirectHandler, Request, build_opener

class NoRedirect(HTTPRedirectHandler):
    def redirect_request(self, request, file, code, message, headers, new_url):
        return None

request = Request(
    'https://api.nixflex.com/v1/agents/agent_example',
    method='PUT',
    headers={'Authorization': 'Bearer ' + os.environ['NIXFLEX_API_KEY'], 'Content-Type': 'application/json'},
    data='{"require_booking_confirmation":true}'.encode('utf-8'),
)
with build_opener(NoRedirect).open(request, timeout=30) as response:
    result = json.load(response)
# Use the result privately; do not log account or caller data.
```

The agent default is false. A number can store true, false or null; null inherits the agent. Apply a number override with the number PATCH endpoint when it needs a different policy.

## Contact approval always comes first

For a new booking, ask the name, read it back and get a clear yes. Then ask the email, spell its local part, and get a separate yes for the full address. Say an exact familiar domain as words, for example `s-a-m at gmail dot com`; spell an unusual domain too. Apply the same rule to saved addresses. A correction repeats only that field. Clarifying one uncertain letter clears the old email approval; a yes to that letter does not approve the complete address. Once the address is approved, ordinary later mentions use words and booking success messages can omit it. Appointment lookup, move and cancel require email approval without asking for a new name.

This flow applies to calls and SMS for both calendars, independently of `require_booking_confirmation`. That setting controls the optional final approval of the action and time on calls. Email domain checks do not prove a mailbox exists; a suggested spelling correction requires the person's approval.

When Google invitations are on, say “Google will email you an invite” (or update/cancellation). Google controls delivery. Cal.com handles its own mail. Do not claim inbox delivery or owner notification without evidence. In-call SMS must be enabled and a matching carrier acceptance received before saying “I've texted you the details.”

## 3. Write a narrow instruction

Ask the agent to read back the exact service, date, time and time zone, then wait for the customer’s answer. A changed detail needs a new read-back. Do not describe an attempted booking as confirmed.

## 4. Test the actual outcome

Test an affirmative answer, a correction and an unclear response. Check the actual calendar entry and action result. Confirmation recognition supports its configured forms; it is not a promise that every phrasing or language will be understood.

## 5. Review the result

Read back configuration after a confirmed update. Inspect the call and action result separately; a saved switch is not proof a real business action succeeded. If a write response is lost, reread the object before repeating it.

## Example response

The agent update returns the safe saved agent projection. Check the intended fields in a fresh [agent read](/api-reference/agents/get); call outcomes are separate records.

## Errors and limits

| Condition | Handling |
| --- | --- |
| Number override | Resolve it before assuming the agent value wins. |
| Ambiguous or changed time | Ask again and confirm the new details. |
| Calendar rejects the action | Report that outcome, not a booking success. |
| Text confirmation wanted | In-call SMS needs its separate switch and eligible sender. |
