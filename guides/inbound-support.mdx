**The important part**

- Start with a narrow support task and test questions the source cannot answer.
- Knowledge provides facts; connected actions perform changes, transfers or messages.
- Test a busy or unanswered transfer as well as a successful one.
- Promise a callback only when your team has a real process to review and assign it.

## Before you start

- Use an Owner or Admin login and a connected test number.
- Prepare support information and a real team destination for transfers.

## Steps

<Steps>

<Step title="Write the support role">

<span id="1-write-the-support-role" />

Open the agent and describe the business, tone and support boundaries. Say which requests need a person and what the agent should do when it cannot help. Avoid promising refunds, changes or appointments without a connected action.

</Step>

<Step title="Add reviewed facts">

<span id="2-add-reviewed-facts" />

Keep common facts in the instructions and add detailed policies in **Knowledge base**. Review topics and enable inbound knowledge. Use the knowledge test for factual questions, including a question your source deliberately does not answer.

</Step>

<Step title="Configure the handoff">

<span id="3-configure-the-handoff" />

Set the transfer destination and choose the desired transfer style. Use a team number that will actually be answered. Write a fallback such as taking a message if the transfer does not connect; do not promise guaranteed reconnection.

</Step>

<Step title="Choose useful text replies">

<span id="4-choose-useful-text-replies" />

If you want addresses or links sent during a call, enable **In-Call SMS** and describe when to offer the text. Use short, accurate wording. Sending a text depends on the number, recipient and contact checks.

</Step>

<Step title="Test the three paths">

<span id="5-test-the-three-paths" />

Call your test number and ask a known question, request a text and ask for a person. Check the answer, actual message and receiving phone. Try an unknown question and an unanswered transfer too, then correct the setup.

</Step>

</Steps>

## What happens next

Review early calls for repeated gaps. Update the factual topic when a policy changes and the instructions when the handling rule changes. Knowledge supplies facts; it does not make a missing action available.

## Check the result

| Result | What it means | What to do |
| --- | --- | --- |
| Known fact answered correctly | The intended source was useful. | Keep it current and test related questions. |
| Unknown question | No reviewed answer is available. | Use the handoff or message-taking rule; add a fact only after review. |
| Transfer unanswered | The receiving person did not connect. | Check that the promised fallback happened. |
| Text requested | The agent attempted a permitted message. | Check the actual message and delivery result. |

## Common questions

<AccordionGroup>

<Accordion title="Should all information go in the prompt?">

No. Keep rules and frequently used facts there; use knowledge for detailed information.

</Accordion>

<Accordion title="Can the agent promise a callback?">

Only describe a follow-up process your team actually operates. Review the captured request and assign it to someone.

</Accordion>

<Accordion title="Does a transfer always reach a person?">

No. Busy, unanswered or failed destinations need a tested fallback.

</Accordion>

<Accordion title="Can Members improve the instructions?">

Members can review shared work. Ask an Owner or Admin to save changes.

</Accordion>

</AccordionGroup>
