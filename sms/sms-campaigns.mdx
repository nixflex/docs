## Prerequisites

Keep `NIXFLEX_API_KEY` private on the server and choose the matching API host. Use owned identifiers; SDK and CLI examples need the [documented minimum versions](/sdks/ecosystem#install-a-client). Use an active owned agent and explicit sender. Set `NXF_AGENT_ID` and other example identifiers before using these examples.

## 1. Inspect campaign state

<CodeGroup>

```bash cURL
curl --request GET \
  --url "https://api.nixflex.com/v1/sms/campaigns?status=running&limit=2" \
  --header "Authorization: Bearer $NIXFLEX_API_KEY"
```

```javascript Node
import { Nixflex } from 'nixflex';

const c = new Nixflex({
  apiKey: process.env.NIXFLEX_API_KEY,
  baseUrl: 'https://api.nixflex.com',

```

```python Python
import os
from nixflex import Nixflex

with Nixflex(
```

## 2. Prepare the template and replies

Use `message_template` with values in each recipient’s nested `variables`. Every required placeholder needs a value. Set `reply_context_prompt` for campaign-specific reply context; the number still needs SMS auto-reply enabled and appropriate instructions. The default association window is 168 hours.

## 3. Review and create

POST `/v1/sms/campaigns` with agent, sender, template and recipients. Choose duplicate handling, confirm permission and preview contact hours. `now` requests launch immediately. `schedule` uses `scheduled_date` and may send when due. Do not send `reuse_campaign_id`; SMS creation always creates new work.

## 4. Handle delivery separately

Store `campaign_id` and read campaign state. Sent, delivered and failed counts are distinct. A recipient response can arrive later; message acceptance is not delivery. Unknown transport outcomes must remain unknown rather than being silently resent.

## 5. Control unsent work

Use `POST /v1/sms/campaigns/{id}/cancel` to stop future dispatch, and the documented resume or consent routes when appropriate. Delete removes the campaign and recipient list after stopping waiting work and any running calls. Neither action recalls a sent text. PATCH edits only the fields and states allowed by the API.

Deleting a voice or SMS campaign cancels waiting work, hangs up its running calls, then removes the campaign and recipient list. Calls already made and texts already sent stay in history. Used charges stay in billing; there are no refunds. Owner and Admin can delete; Member cannot. Cancel alone stops future dispatch and lets active calls finish; Delete also requests their hang-up. If hang-up is not confirmed, HTTP 503 `hangup_pending` returns `error.details.deleted:false` and `error.details.retry_pending:true`. Deletion stays queued and continues automatically. Repeating the same DELETE for the same account and ID safely resumes it. A lost response or `deletion_unavailable` is not success: check the list, then repeat that same DELETE if needed. Missing and foreign IDs share HTTP 404. Bulk call deletion and account closure keep separate safety rules.

## Example response

The creation result includes `campaign_id`, accepted and rejected row counts, duplicates and state. Campaign reads expose separate `sent_count`, `delivered_count`, `failed_count` and `reply_count`; do not compute one by subtracting unrelated totals.

## Errors and limits

| Condition | Handling |
| --- | --- |
| Missing template value | Correct the recipient data before creation. |
| Duplicate policy warn | It does not stop launch; choose reject if needed. |
| Contact or consent hold | Resolve the reason on existing work. |
| Unknown send result | Reconcile; do not create a replacement campaign automatically. |
| Size | At most 100,000 accepted rows; body limits can apply earlier. |
