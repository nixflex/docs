The API uses standard HTTP status codes. A `2xx` status means success, a `4xx` status means something was wrong with your request, and a `5xx` status means something went wrong on our side.

Every error response has the **same shape**: a JSON body with an `error` object. This is consistent across every endpoint, so you can parse errors the same way everywhere.

```json
{
  "error": {
    "type": "invalid_request",
    "code": "invalid_url",
    "message": "webhook_url must be an https URL",
    "doc_url": "https://docs.nixflex.com/errors/invalid_url",
    "details": {}
  }
}
```

## The error object

| Field | Description |
| --- | --- |
| `type` | The broad category of error, derived from the HTTP status (see below). Useful for grouping. |
| `code` | A stable, machine-readable code for the specific error (e.g. `invalid_url`, `not_found`). **Branch on this in your code** rather than matching the message text. |
| `message` | A plain-language description of what went wrong. Safe to show to a human; do not match on it programmatically as wording may change. |
| `doc_url` | A link to documentation about this error code. |
| `details` | An optional object with extra context about the error. May be empty. |

<Note>
  Branch on `error.code` (stable) or `error.type` (broad), never on `error.message` (the wording can change). Check the HTTP status code first to decide how to react.
</Note>

## Error types

The `type` field is derived from the HTTP status code:

| Status | `type` |
| --- | --- |
| `400`, `422` | `invalid_request` |
| `401` | `authentication_error` |
| `402` | `payment_required` |
| `403` | `permission_denied` |
| `404` | `not_found` |
| `409` | `conflict` |
| `5xx` | `server_error` |

## Status codes

| Code | Meaning | What to do |
| --- | --- | --- |
| `200` | Success | Use the response. |
| `201` | Created - a new resource was made | Use the returned resource. |
| `400` | Bad request - a field in your request was invalid | Read `error.code` and `error.message` and fix the request. |
| `401` | Unauthorized - your API key is missing or invalid | Check your API key. See [Authentication](/authentication). |
| `402` | Payment required - insufficient balance | Top up your credit. |
| `404` | Not found - the agent, call, or resource does not exist | Check the ID in your request. |
| `409` | Conflict - the resource already exists | Read the message; you may be creating a duplicate. |
| `500` | Server error - something went wrong on our side | Safe to retry, ideally with a short backoff. |

## Common errors

Missing or invalid API key:

```json
// 401
{
  "error": {
    "type": "authentication_error",
    "code": "unauthorized",
    "message": "Invalid or missing API key",
    "doc_url": "https://docs.nixflex.com/errors/unauthorized",
    "details": {}
  }
}
```

A field is too long:

```json
// 400
{
  "error": {
    "type": "invalid_request",
    "code": "prompt_too_long",
    "message": "system_prompt too long. Maximum is 16000 characters (about 4000 tokens).",
    "doc_url": "https://docs.nixflex.com/errors/prompt_too_long",
    "details": {}
  }
}
```

A field the engine owns:

```json
// 400
{
  "error": {
    "type": "invalid_request",
    "code": "engine_only_field",
    "message": "open_item is written by the engine after each call and cannot be set. Send only: name, email, phone, location, reference_id, preference.",
    "doc_url": "https://docs.nixflex.com/errors/engine_only_field",
    "details": {}
  }
}
```
Resource not found:

```json
// 404
{
  "error": {
    "type": "not_found",
    "code": "not_found",
    "message": "Agent not found",
    "doc_url": "https://docs.nixflex.com/errors/not_found",
    "details": {}
  }
}
```

Server error:

```json
// 500
{
  "error": {
    "type": "server_error",
    "code": "server_error",
    "message": "An unexpected error occurred",
    "doc_url": "https://docs.nixflex.com/errors/server_error",
    "details": {}
  }
}
```

## The Web agent endpoint is different

The public widget endpoint (`POST /v1/widget/message`) never returns a hard error to the visitor's browser. It always responds with `200` and an `ok` flag:

```json
{ "ok": true, "reply": "We are open Mon to Fri, 8:30am to 5:30pm." }
```

If something goes wrong, it still returns `200` with `ok: false` and a short reason, so your widget can show a friendly fallback instead of breaking:

```json
{ "ok": false, "reason": "server_error" }
```

## Debugging with request IDs

Every API response includes an `x-request-id` header, like `req_a1b2c3d4e5f67890`. This ID identifies that exact request in our systems.

When something fails:

1. Grab the `x-request-id` from the response headers.
2. Open **Dashboard &rarr; Logs** and paste it into the search box. The exact request appears with its full (redacted) request and response bodies, status, and timing.
3. Use **Copy as cURL** on the expanded row to replay the request from your terminal - swap in your real API key and any redacted `***` values first.

The Logs page also lets you filter by method, status class (4xx, 5xx), and date range, and shows a summary of your most common error from the last 24 hours.

If you contact support about a failed request, include the request ID - it takes us straight to the exact request.
## Handling errors well

<Steps>
  <Step title="Check the status code">
    A `4xx` means fix your request. A `5xx` means our side - safe to retry.
  </Step>
  <Step title="Branch on error.code">
    The `code` is stable and machine-readable. Use it to decide how your app reacts. Show `error.message` to a human if needed.
  </Step>
  <Step title="Retry 5xx with a short backoff">
    For a `500`, wait a moment and try again. Do not retry in a tight loop.
  </Step>
</Steps>
